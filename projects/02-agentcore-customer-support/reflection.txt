In this project, I connected order tracking and refund tools through AgentCore Gateway and used AgentCore Memory to retain customer context. One design decision was to validate refund responses before saving the interaction. An AfterInvocationEvent audit runs before the memory persistence hook and builds the customer receipt from verified tool results. This prevents an unsupported statement from becoming a stored fact. For example, a refund approval should not also promise a return label unless the label tool actually returned one. The validation adds no extra model call.

The main challenge was that a successful tool call did not always produce an accurate final answer. During testing, the agent claimed that a return label was available even though no label tool had been called. In another response, it expanded the catalog's IPX8 rating into specific water depth and duration claims that the retrieved text did not contain. I inspected the debug tool traces and compared them with the final responses. I added the refund receipt audit, placed it before memory persistence, and tightened the RAG instructions to prohibit unsupported expansions of ratings and specifications. Regression tests against the deployed runtime confirmed that the refund response used verified results and the product response stayed within the retrieved evidence.

For production, customer identity and refund reliability would need stronger controls. The lab accepts a customer ID in the request, but a real service should derive that identity from authentication and enforce order ownership in the backend. Refunds would also need durable idempotency: if a request times out after a refund is approved, retrying it must return the existing transaction instead of issuing another refund. The current demo prevents repeated refund attempts within one invocation, which is useful for testing but does not provide that protection across sessions or service restarts.
